# 重排改成「按场景判定」两档

日期：2026-09-21

## 为什么要改

现在的问法是**一个商品角色一次请求**：拿「折叠露营桌」去问它召回回来的 50 条候选「你是不是折叠露营桌的采买对象」。

问题有两个：

1. **同一个 SKU 被反复问。** 一家店 302 个角色、15,100 个候选位，去重后其实只有 3,605 个 SKU —— 平均每个 SKU 被问了 4 遍。
2. **问的事情不对。** 运营挑货问的是「这个场景需要什么」，不是「每个角色名义上指向什么」。角色只是展示用的分组方式。

## 改成什么

- 判定单位从**商品角色**改成**场景**。
- 一个场景先把召回回来的 SKU **去重**，一份清单。
- 一个场景**一次请求**，把去重后的全部产品塞进去。
- 每个 SKU 只问一次：**这个产品和这个场景相不相关**。
- **两档**：相关 / 不相关。去掉 `same`。
- 问句里**只放产品的英文名**，中文名、角色名、问话都不放。
- 「相不相关」这句话放 state 里，一个请求付一次。
- **展示不变**：结果页还是按商品角色分组列出各自召回的 SKU，只是同一个 SKU 在几个角色下出现时，相关性标签是同一个。

## 实测省多少

| 做法 | 问题数 | 一家店花费 |
| --- | --- | --- |
| 最初（按角色问，每问带一遍口径） | 15,100 | $0.116 |
| 按角色问，口径进 state | 15,100 | $0.045 |
| 改法（场景级去重） | 7,612 | **$0.0096（实测）** |

问题数：shopee-15005th 15,100 → 7,612（省 50%）；shopee-13021ph 12,800 → 8,614（省 33%）。

## 支撑这次改动的一组实测

全部是在改动前用真实 API 量出来的：

| 量什么 | 结果 |
| --- | --- |
| 问题 key 用 SKU vs 用序号 | 都是 908 input tokens，**key 不花钱** |

| 英文名有没有空的 | 8,538 个 SKU 里 0 个为空 |

## 我自己拿的主意

这几条是上面的需求里没提到、我自己定的：

1. **state 的字段名和那句话**：`{场景, 这个场景要卖的商品, 判定说明}`，判定说明写的是「下面每个问题是一件候选商品，判断它和这个场景相不相关。」你要的是「直接写相关和不相关就好了」，所以我没有再写「周边也算相关」那句。
2. **排序里库存的三档**：有货 → 这次没查库存 → 没货。依据是老规矩「没查不等于没货」。
3. **DeepSeek 切片**：它要把无关的 SKU 整条写出来，一个场景一次装不下，我按 300 条一个请求切片。这条你没说过。
4. **英文名为空时回退中文名**：实测 8,538 个 SKU 没有空的，纯保险。
5. **缓存文件名** 从 `role-*.json` 改成 `scene-*.json`。
6. **两档的选项名**保留英文 `related` / `unrelated`，值给 null，和你的示例一致。
7. **Jev 的超时**从 120 秒提到 180 秒：一个场景一个请求，比以前一个角色一个请求大得多。

## 判定口径改了两轮

第一轮实测之后发现 `蛋卷桌`（英文名 `Roll-Top Camping Table`）在「小户型公寓日常用餐区」被判成不相关，而同一族的 `蛋卷折叠桌`（英文名 `Folding table`）判成相关。**模型只看得到英文名，那个 Camping 就是它看到的全部差别。**

于是 `STATED_ONCE` 那句话后面加了两段，都是说明「相关」该多松：

1. 「这个场景用得上、卖得掉就算相关；同一个商品换个用途、换个场合能用上的，也算相关。只要在这场景里有合理用途，哪怕不是主力商品，也判相关。」
2. 「商品名字里带着某个用途（比如 Camping、Outdoor），不代表它就不能用在别的场合，要看商品本身能不能用。」

这两段放在 `state` 里，一个请求付一次，不是每个问题付一次。两段加起来约 1,280 tokens（8 个场景），约 **$0.00005**。DeepSeek 的系统提示词同步改了。

**注意阈值不是这个问题的解法。** 判定这个标签是模型自己选出来的；阈值只管在「排除」模式下，一条「不相关」的把握有没有过线、过线才真删。调低只会删得更多，永远不会把不相关变成相关。默认是「不排除」，一条都不删。
